# The store

zemi keeps its state in SQLite: a global database at `<state>/zemi.db` (skill enabled state, `kv`) and one per project at `<state>/projects/<hash of the trust root>/zemi.db` (`ZEMI_STATE_HOME`, default `~/.local/state/zemi`; the `root` file beside it names the project). A repository's subdirectories and worktrees share its project store.

Reach for the store when the CLI does not expose what you need: the chat log's rows, what a tool call returned, a saved config pick (`zemi db "select seq, kind, text from log order by seq desc limit 20"`). Anything else:

```sh
zemi db "select id, title, updated_at, cost from sessions order by updated_at desc limit 5"
zemi db "select tool_calls.tool, tool_calls.ok from tool_calls join messages on tool_calls.message_id = messages.id where messages.session_id = '<id>'"
zemi db "select id, title from sessions where title like ?1 limit ?2" '%test%' 10
zemi db --global "select key, value_json from kv where key like 'config:%'"
```

The first argument is the whole query, so quote it; the rest bind to its numbered placeholders - the first is `?1`, the second `?2`, and the number, not the position in the query, picks the argument. Values bind as text; SQLite's column affinity compares them against typed columns, so `'24'` works for an integer column and in `LIMIT`. A placeholder with no argument binds as NULL and an extra argument is ignored, so keep the count right. Text output is an aligned table capped at 500 rows, NULL an empty cell, a cell cut past 60 wide with its cut count (`... (+N chars; --json for the whole)`); `--json` prints one object per row and caps nothing. `--global` reads the global store; the default is this project's, and `-C <dir>` reads another project's.

A tool call writes two tool-role rows: a content row with the result (`tool_call_id` at `$.content[0].data.tool_call_id`, output text at `$.content[0].data.output.data.text`, error text at `$.content[0].data.output.data.error`) and a stub row `{"tool": name}` that `tool_calls.message_id` points at. So `tool/ok` joins go through the stub, while the result text needs the content row, matched by `tool_call_id` across tool-role rows - rowid adjacency breaks when calls run in parallel.

Agent and workflow runs are session rows with `parent_id` set; the chat itself is the `log` table, one append-only row per message. In SQL, `where parent_id is null` lists the top-level rows and the inverse finds the run ids.

The open is read-only all the way down (`mode=ro` and `query_only`): a write fails, nothing is created or migrated, and a store a running zemi holds is read without waiting on it. One SQLite ceiling survives both: `ATTACH` of a path with no file still makes an empty one. A store this zemi's migrations have not reached is refused: start zemi in its project once to migrate it. A missing store is an error naming its path.

The schema the migrations build, regenerated by `make golden` (the section between the markers is not hand-written):

<!-- schema:begin -->
- `kv` - small state: saved config picks, goals, recap hints, MCP state, user storage
  key TEXT pk, value_json TEXT NOT NULL, updated_at INTEGER NOT NULL
- `log` - the eternal chat: one append-only row per message, seq its dense 0-based index
  seq INTEGER pk, kind TEXT NOT NULL, text TEXT NOT NULL, meta_json TEXT, parts_json TEXT, created_at INTEGER NOT NULL, origin TEXT NOT NULL DEFAULT ''
- `messages` - a subagent run's persisted rows, read back in rowid order
  id TEXT pk, session_id TEXT NOT NULL, role TEXT NOT NULL, parts_json TEXT NOT NULL, created_at INTEGER NOT NULL, row_meta TEXT NOT NULL DEFAULT ''
- `nodes` - the summary tree: node(l, i) covers the 2^l messages from i*2^l on, one line each
  l INTEGER pk NOT NULL, i INTEGER pk NOT NULL, text TEXT NOT NULL, size INTEGER NOT NULL, built_at INTEGER NOT NULL
- `sessions` - the "main" billing and todos anchor, one row per subagent run
  id TEXT pk, parent_id TEXT, title TEXT NOT NULL DEFAULT '', agent TEXT NOT NULL DEFAULT '', created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL, prompt_tokens INTEGER NOT NULL DEFAULT 0, completion_tokens INTEGER NOT NULL DEFAULT 0, cache_read_tokens INTEGER NOT NULL DEFAULT 0, cache_billed_tokens INTEGER NOT NULL DEFAULT 0, cost REAL NOT NULL DEFAULT 0, last_in INTEGER NOT NULL DEFAULT 0, run_status TEXT NOT NULL DEFAULT ''
- `skills` - the skill index synced at boot: path, source and enabled flag per name
  name TEXT pk, path TEXT NOT NULL, source TEXT NOT NULL, enabled INTEGER NOT NULL, created_at INTEGER NOT NULL
- `todos` - a session's todo list
  id INTEGER pk, session_id TEXT NOT NULL, content TEXT NOT NULL, status TEXT NOT NULL, active_form TEXT NOT NULL DEFAULT '', ord INTEGER NOT NULL, created_at INTEGER NOT NULL
- `tool_calls` - one row per tool call a message carried
  id INTEGER pk, message_id TEXT NOT NULL, tool TEXT NOT NULL, ok INTEGER NOT NULL, created_at INTEGER NOT NULL
- `usage_days` - the bill summed per UTC day, which /usage reads for today, the week and all time
  day TEXT pk NOT NULL, prompt_tokens INTEGER NOT NULL DEFAULT 0, completion_tokens INTEGER NOT NULL DEFAULT 0, cost REAL NOT NULL DEFAULT 0
- `view_lines` - the persisted view, oldest first; a line whose node is missing renders as a placeholder
  ord INTEGER pk, l INTEGER NOT NULL, i INTEGER NOT NULL
<!-- schema:end -->
